# Dev, pro и развёртывание на этом компьютере

[Español](../DEPLOYMENT.md) · [English](../en/DEPLOYMENT.md) · **Русский**

## Cloudflare и запуск компьютера

Подключённый репозиторий: `Eddierh/reservet`. Раннер: `reservet-pc`, метка
`reservet-server`, каталог `E:\actions-runner-reservet`.
Планируемые адреса: `reservet-dev.log14.com` → 3100 и `reservet.log14.com` → 3200.
Выполните `cloudflared tunnel login`, разрешите доступ к `log14.com` в браузере, затем:

```powershell
./deploy/Configure-Tunnel.ps1
./deploy/Start-Server.ps1
```

Первый скрипт создаёт или использует туннель `reservet-pc` и добавляет DNS без
перезаписи существующих записей. Конфигурация хранится вне Git:
`E:\reservet-server\config\cloudflared.yml`. Не публикуйте сертификат и JSON с секретами.
Второй запускает Desktop, раннер и туннель в фоне. Логи: `E:\reservet-server\logs`.
Ярлык `Reservet Server` в автозагрузке Windows запускает скрипт при входе этого
пользователя; работа до входа в Windows не гарантируется.

Cloudflare принимает HTTPS и подключается к локальным портам исходящим туннелем.
Не открывайте порты роутера. DNS не добавляет вход в систему: URL доступен другим,
пока не реализована аутентификация или Cloudflare Access. Проверьте локальный
`/health/db` и внешний HTTPS-адрес перед признанием развёртывания завершённым.

## Окружения

| Назначение          | Ветка     | Локальный адрес       | Проект Compose   | База                              |
| ------------------- | --------- | --------------------- | ---------------- | --------------------------------- |
| Работа разработчика | Любая     | http://localhost:3000 | Исходный Compose | reservet, порт 5433               |
| Развёрнутый dev     | `develop` | http://localhost:3100 | `reservet-dev`   | reservet_dev, порт не опубликован |
| Развёрнутый pro     | `main`    | http://localhost:3200 | `reservet-pro`   | reservet_pro, порт не опубликован |

У окружений отдельные сети, тома и пароли, но общий компьютер и движок Docker:
от поломки компьютера такое разделение не защищает. `NODE_ENV=production` в обоих
окружениях запускает скомпилированный код, а `APP_ENV` различает dev/pro.
Исходный Compose остаётся для локального обучения.

## Пайплайн

Проверки pull request выполняются на GitHub, никогда на этом компьютере.
Push в `develop` или `main` запускает `deploy.yml`: проверку кода, форматирования,
типов, тесты и сборку. Затем создаётся Docker-образ с SHA коммита в теге.
GitHub запускает тестовый PostgreSQL, дважды выполняет миграции, запускает
приложение и проверяет `/` и `/health/db`. Тот же проверенный образ передаётся
как артефакт Windows-раннеру на этом компьютере.

`develop` развёртывается в dev, `main` — в pro. Для pro перед миграцией создаётся
резервная копия, затем приложение запускается и проверяется. Развёртывания одного
окружения не пересекаются. Workflow можно запустить вручную из Actions, выбрав
`main` или `develop`. После подключения push в `main` автоматически обновляет pro.

## 1. Docker и конфигурация

Установите [Docker Desktop для Windows](https://docs.docker.com/desktop/setup/install/windows-install/),
выберите контейнеры Linux и проверьте `docker info` и `docker compose version`.
Compose должен поддерживать `up --wait` и `--wait-timeout`.

Из корня проекта:

```powershell
./deploy/Initialize-Server.ps1
```

На этом компьютере команда уже выполнена. Существующие файлы она сохраняет.
Создаёт `E:\reservet-server\config\dev.env` и `pro.env` с независимыми случайными
паролями. Права Windows ограничиваются текущим пользователем, SYSTEM и
администраторами. Раннер должен работать от этой учётной записи или получить
отдельное разрешение. Не добавляйте файлы в Git и не публикуйте в логах.
Секреты не включаются в образы и артефакты.

Для другого каталога передайте `-ServerRoot 'D:\reservet-server'` и укажите тот
же путь в переменной репозитория `RESERVET_SERVER_ROOT`. Изменение файла само по
себе не меняет пароль уже созданного пользователя PostgreSQL: нужен также SQL.

## 2. Подключение GitHub к компьютеру

1. Загрузите проект в **закрытый** репозиторий с ветками `main` и `develop`.
2. В Settings → Environments создайте `dev` и `pro`. Разрешите развёртывание
   dev только из `develop`, pro — только из `main`.
3. Защитите обе ветки: требуйте pull request и успешные проверки. Право менять
   код развёртывания должно быть только у доверенных участников.
4. В Settings → Actions → Runners → New self-hosted runner выберите Windows x64.
5. Выполните актуальные команды скачивания и регистрации, показанные GitHub,
   в отдельном каталоге, например `E:\actions-runner-reservet`, вне репозитория
   и данных сервера. Добавьте метку **`reservet-server`**.
6. Запускайте раннер от пользователя с доступом к Docker и конфигурации.
   Сначала проверьте `docker info` от того же пользователя в той же сессии.
7. Убедитесь, что раннер Online, и выполните push в `develop`.
8. Проверьте Actions и откройте http://localhost:3100.
9. Объедините изменения в `main` через pull request и проверьте http://localhost:3200.

Для регистрации нужен временный токен GitHub; не сохраняйте его в репозитории.
Раннер устанавливает исходящие соединения, открывать входящие порты для заданий
GitHub не нужно. См.
[документацию раннеров](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners?platform=windows).

## 3. Эксплуатация и восстановление

Docker Desktop должен оставаться запущенным. Настройте его запуск при входе в
Windows и исключите сон компьютера на время обслуживания. `restart: unless-stopped`
перезапускает контейнеры при возвращении движка, но не запускает Docker или раннер.
Раннер-служба должен иметь доступ к тому же движку. Проверьте полную перезагрузку
компьютера перед признанием сервера доступным. Docker Desktop/WSL не гарантирует
работу до входа в систему; для такой эксплуатации рассмотрите Linux VM с Docker Engine.

Просмотр dev с SHA развёрнутого коммита:

```powershell
$env:APP_IMAGE = 'reservet:<SHA-из-40-символов>'
docker compose -p reservet-dev --env-file E:\reservet-server\config\dev.env -f deploy/compose.yaml ps
docker compose -p reservet-dev --env-file E:\reservet-server\config\dev.env -f deploy/compose.yaml logs --tail 100 app
```

Копии pro находятся в `E:\reservet-server\backups\pro`, последняя успешная версия —
в `releases\<окружение>\current.txt`. Копии перед развёртыванием не заменяют
регулярное резервирование: сохраняйте их и вне компьютера, определите срок хранения,
проверяйте восстановление на временной базе, никогда сразу на pro. Следите за
диском: образы и копии сохраняются без автоматической разрушительной очистки.

Сбой копирования или миграции останавливает развёртывание до замены приложения.
Сбой запуска помечает развёртывание неуспешным и может потребовать ручного
восстановления. Автоматического отката приложения или базы нет. Подтверждённые
миграции остаются применёнными. Изменения схемы должны быть совместимы с предыдущей
версией, которая может продолжать работать во время миграции. Восстановление
копии может потерять записи, сделанные после её создания.

Ручное развёртывание уже загруженного образа:

```powershell
./deploy/Deploy.ps1 -Environment dev -Revision <SHA-из-40-символов>
```

Для возврата к старой версии сохраните или загрузите её образ и проверьте
совместимость с текущей схемой. Не удаляйте тома для исправления развёртывания.

## Доступ и текущее состояние

Порты 3100 и 3200 привязаны к `127.0.0.1` и доступны только на этом компьютере.
Правила firewall, роутер и туннели не изменялись. Для внешнего доступа нужно
определить домен/сеть, HTTPS и реализовать аутентификацию и авторизацию силами разработчика.

Docker Desktop, WSL и раннер установлены на этом компьютере. GitHub проверяет
образ и реальные миграции перед передачей артефакта. Результат последнего
развёртывания смотрите в Actions: успешные проверки GitHub ещё не означают, что
развёртывание на компьютере завершено. Для внешнего доступа авторизуйте Cloudflare,
создайте маршруты и проверьте оба HTTPS-адреса.
